# 專案結構

Go 服務的目錄規範。hestia 和 [themis](https://github.com/danicotech/themis) 共用同一套,themis 只多一個「活動」維度。

這份文件描述的是**預期設計**,程式碼還沒進來。目錄先立好、規則先寫死,是為了讓第一行程式碼就落在對的位置 —— 分層這種事,寫完再回頭抽的成本是一開始就分好的三倍。

## 最外層

```text
cmd/          進入點。一個子資料夾一個 binary
config/       設定的結構定義與載入
e2e/          黑箱測試,打真的 HTTP、連真的 DB
internal/     所有實作。Go 保證外部模組 import 不到
contracts/    匯出的 OpenAPI 與渲染契約(發布物)
migrations/   goose
deploy/       compose 與部署設定
docs/
```

`cmd/`、`config/`、`e2e/`、`internal/` 是程式碼的四個根,其他都是資料。

**`cmd/` 底下一個資料夾一個 binary。** 目前只有 `cmd/server/`。排程先跟 server 同進程跑,等到「排程卡住 API」或「要獨立擴縮」其中一件真的發生,再拆 `cmd/worker/` —— 那時是搬 wire 的組裝,不是搬邏輯。

## internal 的六層

```text
internal/
├── shared/           跨層共用的基礎設施無關工具
├── domain/           實體、值物件、領域錯誤、port 介面。純的
├── core/             用例。編排 domain,決定交易邊界
├── cron/             排程與背景工作
├── infrastructure/   adapter。實作 domain 定義的 port
└── interface/        對外的入口:http / websocket / grpc
```

### 依賴方向只有一個

```text
interface ──┐
            ├──▶ core ──▶ domain ◀── infrastructure
cron ───────┘                            (實作 domain 的 port 介面)
```

四條推論,每一條都值得做成 CI 檢查:

1. **`domain` 不 import 任何其他層。** 沒有 gin、沒有 pgx、沒有 huma、沒有 redis。它只認 `context` 和標準庫。
2. **`core` 不 import `interface` 與 `infrastructure`。** 它只認 `domain` 定義的 port 介面。
3. **`interface` 不 import `infrastructure`。** handler 拿到的是 `core` 的用例介面,不是 `*pgxpool.Pool`。
4. **只有 `cmd/` 知道具體型別是誰。** 介面接到哪個實作,是 wire 在組裝時決定的,其他地方一律看不到。

第 4 條是前三條能成立的原因。少了它,前三條會在某個趕時間的下午被一句 `import "internal/infrastructure/storage/postgres"` 破掉。

### 每層放什麼

| 層 | 放 | 不放 |
|---|---|---|
| `shared/` | error 型別與包裝、logger 介面、clock、id 產生器、分頁參數、冪等鍵的計算 | 任何領域概念、任何第三方 client |
| `domain/` | entity、value object、狀態機、領域錯誤、**repository 介面** | SQL、HTTP、序列化標籤 |
| `core/` | 用例(下注、兌換、綁定)、交易邊界、跨聚合的編排 | HTTP 狀態碼、gin.Context、DTO |
| `cron/` | 對帳 job、outbox dispatcher、過期清理 | 業務規則(呼叫 `core` 的用例) |
| `infrastructure/` | pgx / redis / SMTP / 簡訊 / Meta 的實際呼叫,repository 實作 | 業務判斷 |
| `interface/` | 路由、DTO、驗證、認證、把 `core` 的錯誤翻成 HTTP 狀態 | 領域規則、直接下 SQL |

`shared/` 最容易爛掉。判準只有一句:**如果一個東西需要知道「代幣」或「賽事」是什麼,它就不屬於 `shared/`。** 放不進其他層不是留在這裡的理由。

### domain 與 core 的分界

分不清的時候問:**這條規則沒有資料庫也成立嗎?**

- 「賠率上限是 12」「串關總倍數不得超過 300」→ `domain`
- 「扣款、寫帳本、建注單要在同一個交易裡」→ `core`

`domain` 定義 port,`core` 使用 port,`infrastructure` 實作 port。介面**宣告在使用它的那一側**(`domain`),不是實作那一側 —— 這樣 `domain` 才不會為了拿介面而反過來 import `infrastructure`。

### platform 與 activity 這條線

每一層底下再切模組:

```text
internal/domain/
├── platform/     identity / ledger / outbox / redeem
└── activity/     賽事規則、賽程樹、賠率、注單
internal/core/
├── platform/
└── activity/
```

**規則:任何 `platform/` 底下的套件,不得 import 任何 `activity/` 底下的套件。** 反向可以,但只能透過 `domain/platform` 宣告的 port(例如 `Ledger`),不准碰 `platform` 的實體內部。

這是整個專案唯一真正回不去的決定。守住的話,第二個活動要辦時抽出 themis 就是把每一層的 `activity/` 子套件一起拎走;破了就是重寫。

值得寫一條 CI 檢查擋住 —— 這種紀律靠自律撐不過三個月。

## infrastructure

```text
infrastructure/
├── storage/          有狀態的資料存放,我們自己維運的
│   ├── postgres/     pgxpool、sqlc 生成的查詢、repository 實作、交易管理
│   └── redis/        快取、扇出、速率限制的桶子
├── queue/            asynq
└── notifier/         email / sms / meta,各家一個檔案,同一個介面後面
```

`storage/` 這層資料夾是有意義的,不是為了分類好看:**它圈出的是「掛了會掉資料」的東西**。備份、migration、健康檢查、連線池調校都只看這個資料夾。第三方 API(Meta、簡訊商)掛掉是重試問題,資料庫掛掉是事故,兩者的維運方式不同,不該混在同一層。

之後新增的第三方服務照這個判準放:**存我們的資料**就進 `storage/`,**送東西出去**就跟 `notifier/` 一起,**排隊**就進 `queue/`。

交易邊界的實作放 `storage/postgres/`,但**交易的範圍由 `core` 決定** —— 用一個 `UnitOfWork` 之類的 port 表達,不要讓 handler 或 repository 自己決定要不要開交易。

## interface

```text
interface/
├── http/
│   ├── dto/          請求與回應的結構,huma 的輸入輸出型別
│   ├── handler/      operation 實作,一個用例一個方法
│   ├── middleware/   認證、代理身分、request id、log、recover、速率限制
│   └── router/       路由註冊表:把 operation 掛到路徑上
├── websocket/        即時推播的連線管理與扇出
└── grpc/             目前沒有消費者,先保留位置
```

`grpc/` 現在是空的。stentor 走 HTTP + JSON,theatron 也是,沒有東西需要 gRPC。**保留位置不等於要去填滿它** —— 等真的出現一個吃 streaming 或跨語言型別的內部消費者再說。

### handler 與 router 的分工

用 huma 之後這兩個容易糊在一起,所以先講死:

- **`router/`** 是**註冊表**。`huma.Register` 的呼叫集中在這裡:operation id、method、path、summary、tags、錯誤碼、需要哪些 middleware。一個檔案就能看完整張 API 表。
- **`handler/`** 是**實作**。只有 `func(ctx, *dto.XxxInput) (*dto.XxxOutput, error)`,裡面呼叫 `core` 的用例、把領域錯誤翻成 huma 的錯誤型別。不碰路徑字串。

分開的好處是改路徑、加 tag、調 OpenAPI 描述都不用動到 handler 檔案。

### middleware 有兩種,別放錯

| 種類 | 寫在哪 | 用在什麼 |
|---|---|---|
| gin middleware | `middleware/`,在 router 組裝時掛上 | recover、request id、CORS、log、靜態的速率限制 |
| huma middleware | 同樣放 `middleware/`,但走 huma 的註冊 | 需要拿到 operation 資訊的(依 operation 決定權限、依 operation 決定冪等要求) |

判準:**需要知道「這次呼叫的是哪個 operation」的,寫成 huma middleware;只認 HTTP 的,寫成 gin middleware。**

### dto 不是 domain entity

即使欄位一模一樣也要分開。DTO 有序列化標籤、有驗證規則、有 huma 的 schema 資訊,而且它會為了相容性而保留欄位;entity 不該為了 API 相容性長出包袱。轉換寫在 `handler/` 裡。

## 技術選型

| 用途 | 選擇 | 理由 |
|---|---|---|
| HTTP router | gin | middleware 生態最大,團隊熟悉度高 |
| API 層 | huma v2(`humagin` adapter) | 從 Go struct 產生 OpenAPI 3.1、自動驗證、自動內容協商 |
| DI | wire | 編譯期組裝。錯的接線是編譯錯誤,不是半夜的 nil pointer |
| Driver | pgx/v5 + pgxpool | Postgres 原生協定 |
| Query | sqlc | 寫真 SQL,拿型別安全的 Go code |
| Migration | goose | 可 embed 進 binary |
| 佇列 | asynq | outbox 派送、重試與退避 |
| 測試 | testcontainers-go | e2e 對真的 Postgres 跑 |

### huma 換到什麼、付了什麼

換到的:**OpenAPI 不會過期**。它從實際跑的型別產生,不是另外維護的一份文件。加上驗證、錯誤格式(RFC 9457)、內容協商都免費。

付的代價有兩個,都要知道:

1. **契約方向反轉。** 原本規劃是 spec-first(`openapi.yaml` → `oapi-codegen` → Go 骨架),huma 是 code-first(Go 型別 → spec)。規則因此改寫,見下一節。
2. **多一層 gin。** huma 也能直接跑在 `net/http` 上(`humago`),那樣少一層 adapter。選 gin 是為了它的 middleware 生態;如果半年後發現 middleware 幾乎都寫成 huma 的,那就該把 gin 拿掉 —— 換掉的成本只有 `router/` 一個檔案,這是刻意留的退路。

### 契約規則(取代架構規劃書 §36 的機制)

```text
Go 的 dto 型別  ← 唯一來源
      ↓  CI 匯出
contracts/platform/openapi.yaml   ← 發布物,進版控
      ↓  CI 比對:與匯出結果不一致就紅燈
      ↓  CI 發佈 npm
@danicotech/platform-api          ← theatron 與 stentor 用版本相依安裝
```

結論沒變,只是來源換了一邊:

- **Go 這側**:改型別就是改契約,不用手動同步。
- **TS 這側**:一樣禁止手寫 API 型別,只能 import 生成的 client。
- **防漂移**:`contracts/` 裡的 spec 必須是 CI 匯出的結果。有人改了型別卻沒重新匯出 → CI 擋下來。

**渲染契約(給 stentor 的顯示描述)是例外,仍然是手寫的 spec。** 因為它的消費者是 TypeScript,而定義它的 Go 型別只是實作細節之一 —— 那份契約要先於任何實作存在。

### wire 怎麼擺

```text
每個套件自己宣告 ProviderSet
  infrastructure/storage/postgres.ProviderSet
  core/platform.ProviderSet
  interface/http.ProviderSet
        ↓
cmd/server/wire.go       injector,//go:build wireinject
cmd/server/wire_gen.go   生成的結果,進版控
```

三條規則:

1. **`ProviderSet` 宣告在自己的套件裡**,不要開一個 `internal/di/` 把所有接線集中 —— 那會變成唯一一個 import 了所有層的套件,分層就白分了。
2. **介面綁定用 `wire.Bind`** 把 `*postgres.LedgerRepo` 綁到 `domain.LedgerRepository`。這是「只有 cmd 知道具體型別」的實際落點。
3. **`wire_gen.go` 進版控**,CI 檢查重新生成後沒有 diff。

## 一個請求走過的路徑

以「下注」為例,照這個順序放檔案:

```text
router/bet.go          註冊 POST /v1/bets,標明需要冪等鍵
  → middleware/        驗 token、解析 X-Acting-User、檢查 Idempotency-Key
  → dto/bet.go         PlaceBetInput / PlaceBetOutput,欄位驗證由 huma 做
  → handler/bet.go     轉成 core 的參數,呼叫用例,翻錯誤
  → core/activity      開交易 → 驗階段 → 重算賠率 → 扣代幣 → 寫帳本 → 建注單 → 寫 outbox
      → domain/activity     賠率公式、串關上限、階段守衛
      → domain/platform     Ledger port
  → infrastructure/storage/postgres   交易與 SQL 的實際執行
```

如果某個步驟你不知道該放哪一層,通常代表那一步同時做了兩件事。

## 測試

| 層級 | 位置 | 對象 |
|---|---|---|
| 單元 | 各套件內 `_test.go` | `domain` 的規則。不需要任何 mock,這是分層的回報 |
| 整合 | `infrastructure/**/_test.go` | repository 對真的 Postgres(testcontainers) |
| 端對端 | `e2e/` | 起完整服務,打真的 HTTP |

`e2e/` 是黑箱:**只能透過 HTTP 和資料庫斷言,不准 import `internal/`。** 一旦它 import 了內部型別,重構就會連帶改測試,而 e2e 存在的意義就是重構時它不用改。

用 build tag(`//go:build e2e`)隔開,預設的 `go test ./...` 不跑它。

最該優先寫 e2e 的是**併發與冪等**:同時送兩筆相同 `Idempotency-Key` 的下注、同一場比賽被結算兩次。這兩種 bug 用單元測試抓不到,而它們正好是這個系統最貴的 bug。

## 設定

```text
config/
├── config.go       結構定義與預設值
└── *.yaml          各環境的非機密設定
```

機密一律走環境變數,不進版控。變數前綴是 `PLATFORM_`,不是 `HESTIA_` —— 凌晨三點看 log 的人不該還要查神話辭典。

`config` 在 `internal/` 外面是刻意的:它只有型別和載入邏輯,沒有業務語意,`cmd/` 和測試都要用。

## 什麼時候不該加資料夾

這套結構已經比多數專案深。**不要因為某層「看起來該有」就先開資料夾。**

- 一個套件只有一兩個檔案 → 不要為它開子資料夾
- 只有一個實作、而且看不到第二個 → 不要為它抽介面
- 沒有消費者的 `interface/grpc/` → 保持空的比塞進去一個沒人叫的服務好

判準:**這個資料夾解決了哪個現在真的存在的問題?** 答不出來就先不要建。
