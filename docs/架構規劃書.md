## 0. 先講四個判斷

### 判斷一:中繼站不要做成「資料庫代理」

你的描述是「Golang 中繼站服務專門針對資料庫操作」。如果照字面實作 —— 對外暴露的是資料表操作 —— 這個架構會出問題。

```
❌ POST /db/bets  { user_id, stake, odds, potential, status }
```

這樣的介面代表:呼叫端(網頁後端、Bot)得先自己查賠率、算派彩、確認階段、檢查餘額,然後才叫中繼站「把這列寫進去」。**領域規則跑到了呼叫端**,中繼站只是個沒有判斷力的守門員。結果是規則有兩份、race condition 在呼叫端發生、多繞一跳網路卻沒換到任何保證。

正確的邊界是暴露**業務動作**:

```
✅ POST /v1/bets  { legs: [...], stake: 100 }
   → 服務自己驗階段、重算賠率、檢查餘額、扣款、寫帳本、建注單,全在同一個 transaction
```

所以它不是「中繼站」,是**核心領域服務(core)**。網頁和 Bot 都退化成薄薄的呈現層。這個定位一改,後面所有設計都跟著順。

**判斷標準**:如果某個 API 的名字是名詞複數 + CRUD 動詞,它大概錯了;如果名字是「下注」「開賽」「結算」「兌換」,方向對了。

### 判斷二:Discord Bot 用 TypeScript + discord.js

> **後續修正見第 34 節。** 結論不變(仍是 TypeScript),但理由完全不同 ——
> 這裡的理由是「Bot 很薄」,實際上 Bot 是長壽的通用閘道。

先澄清一個前提:**Discord 沒有官方的伺服器端 Bot SDK**。官方維護的是 API 規格、文件,以及給遊戲用的 Social SDK(C++/Unity/Unreal),那個跟 Bot 無關。所有 Bot 函式庫都是社群維護的,「有沒有官方 SDK」這條篩選條件在這裡不成立,要改看生態系成熟度。

| | discord.js (Node/TS) | discordgo (Go) |
|---|---|---|
| 維護 | 社群團隊,約 26.8k stars、每週近 95 萬次 npm 下載 | 單一主維護者為主,社群較小 |
| 型別 | 原生 TypeScript | Go 原生 |
| 新功能跟進 | 最快,元件/Modal/新互動幾乎第一時間支援 | 有落差,新互動元件常要自己補 |
| 適合 | 互動元件密集的 Bot | 高併發、單一執行檔部署 |

**建議 discord.js + TypeScript。** 理由:

1. 賽事 Bot 會大量用到按鈕、下拉選單、Modal(報名、投票、下注選項、管理指令),這正是 discord.js 領先最多的地方。
2. Bot 是 I/O bound 的膠水層,真正的運算在 core。Go 的效能優勢在這裡換不到東西。
3. Bot 的商業邏輯應該幾乎是零 —— 它只把 Discord 互動翻譯成 core 的 API 呼叫。這種程式碼用哪個語言都不痛,選生態系最大的那個。

**不建議 NestJS。** NestJS 的價值在 DI、模組邊界、大型團隊協作。你的 Bot 是薄轉接層,套上 NestJS 只是多背一層框架成本。等 Bot 真的長到十幾個模組再說。

**唯一該選 discordgo 的情況**:你希望整個後端只維護一種語言。這個理由是正當的,單人專案尤其。但代價是新 Discord 功能要自己補,要有心理準備。

### 判斷三:網頁不需要獨立後端

你寫的是「網頁前端和後端,再拋送到 Golang」。實務上這個「後端」應該只是 **BFF(Backend for Frontend)**:管 cookie/session、聚合多次 core 呼叫、做 SSR。它**不該有自己的資料庫**。

Next.js 的 Route Handlers 就能勝任,不必再起一個 NestJS 服務。少一個服務、少一套部署、少一份設定。

### 判斷四:「發文到 IG/FB」和「串流到 IG/FB」是兩件完全不同的事

這兩個常被混在一起,但技術路徑完全不同,難度差很多:

**發文(可行,而且比你想像的簡單)**
Instagram Graph API 的內容發佈。關鍵利多是:因為你只發**自己的**帳號,只需要 Standard Access —— **不用送 App Review,不用商業驗證**。Meta 的規則是「只服務你自己擁有或管理的帳號」就走 Standard Access;要 App Review 的是那些代第三方帳號發文的產品。

前置條件:IG 帳號要轉成 Professional(Business 或 Creator)、連結一個 FB 粉專、建一個 Meta 開發者 App。要注意的實作細節:圖片必須放在公開的 HTTPS URL(不能直接上傳檔案),發文是兩步(先建 media container,等處理完成再 publish)。

**直播串流(基本上不是寫程式的問題)**
IG 對第三方直播 API 幾乎不開放。FB 可以用 Live Video API 取得 RTMP 推流位址,但如果你要的是「把比賽畫面推到社群平台」,實務上就是 OBS 推 RTMP,不需要寫任何整合。

**所以**:規劃階段先把「賽事公告自動發到 IG/FB」列進去(難度中等),「直播串流」從程式範疇拿掉(改成營運流程)。

## 1. 服務拆分與職責

> **已被第 33–34 節取代。** 正確的切線是「平台層 vs 活動層」,不是「核心 vs 呈現層」。

```
                    ┌──────────────┐
   瀏覽器 ─────────▶│  web (BFF)   │──┐
                    │  Next.js     │  │
                    └──────────────┘  │
                                      │  Connect RPC / REST
   Discord ────────▶┌──────────────┐  │
                    │  bot         │──┤
                    │  discord.js  │  │
                    └──────────────┘  │
                                      ▼
                            ┌──────────────────┐
                            │  core (Go)       │
                            │  唯一的領域權威   │
                            └────────┬─────────┘
                                     │
                    ┌────────────────┼────────────────┐
                    ▼                ▼                ▼
              PostgreSQL          Redis          外部服務
              (唯一真實來源)   (快取/佇列/扇出)  (email/SMS/Meta)
```

| 服務 | 職責 | 明確不做的事 |
|---|---|---|
| **core** (Go) | 領域規則、賽事流程、賠率、注單結算、代幣帳本、身分權威、整合派送 | 不管畫面、不管 Discord 互動格式 |
| **web** (Next.js) | 畫面、SSR、cookie session、聚合呼叫 | 不碰資料庫、不算賠率、不決定誰能做什麼 |
| **bot** (TS) | Discord 互動 ↔ core API 的翻譯 | 不存狀態、不算任何業務結果 |

**唯一 DB 憑證在 core。** web 和 bot 的容器裡完全沒有資料庫連線字串 —— 這是一道實質的安全邊界,不是慣例。

### 服務間協定

| 方案 | 優點 | 成本 |
|---|---|---|
| **Connect RPC**(建議) | 一份 `.proto` 產出 Go server + TS client,支援純 JSON over HTTP/1.1,瀏覽器可直連,不需要 Envoy | 要導入 `buf` 工具鏈 |
| OpenAPI + codegen | 工具熟悉度高,`oapi-codegen` + `openapi-typescript` | 規格與實作容易漂移,要靠紀律 |
| 手寫 REST + 手寫型別 | 零工具 | 三個地方各維護一份型別,遲早出事 |

跨語言的專案,**契約自動生成的價值非常高**,值得那點工具鏈成本。

### 身分與授權

core 是唯一的身分權威,簽發短效 access token + refresh token。

- **web**:refresh token 放 httpOnly cookie,BFF 換 access token 後代呼叫。
- **bot**:持 service token,呼叫時帶 `X-Acting-User: discord:<id>` 代理使用者身分。core 用 `users.discord_user_id` 對應到帳號。
- **綁定流程**:網頁登入後產生一次性綁定碼 → 在 Discord 輸入 `/bind <碼>` → core 寫入對應。

## 2. Repo 數量:一個 Monorepo

> **已被第 35 節取代。** 加入「Bot 跨活動複用」的條件後,答案是 4 個 repo。
> 本節保留作為對照。

**建議 1 個 repo。**

理由很單純:專案早期,服務之間的**契約會頻繁改動**。今天在 core 加一個欄位,web 和 bot 都要跟著改。分成三個 repo 意味著每次都要開三個 PR、注意合併順序、還要處理版本相依。這是為「團隊邊界」付的代價,而你現在沒有團隊邊界。

```
tournament/
├── services/
│   ├── core/                 # Go
│   │   ├── cmd/server/
│   │   ├── internal/
│   │   │   ├── domain/       # 純業務規則,不 import 任何基礎設施
│   │   │   ├── postgres/     # sqlc 生成 + repository
│   │   │   ├── redis/
│   │   │   ├── notify/       # email / sms / meta 各家 provider
│   │   │   └── rpc/          # Connect handler
│   │   └── migrations/
│   ├── bot/                  # TypeScript + discord.js
│   └── web/                  # Next.js
├── proto/                    # 契約來源(唯一)
├── gen/                      # 生成的 client,commit 進 repo
├── deploy/
│   ├── compose.yaml
│   ├── compose.dev.yaml
│   └── Caddyfile
├── docs/
└── .github/workflows/        # 用 path filter 分開三條 CI
```

**什麼時候該拆**:某個服務有了獨立的維護者、獨立的發版節奏、或需要不同的存取權限。在那之前拆是純成本。

`buf` / protobuf 工具鏈、OpenTelemetry + Prometheus + Grafana、GitHub Actions、Meta Graph API、SSE / WebSocket 擴展、PostgreSQL 分割表與 replica。

### 建議明確避開

- **ORM(GORM 等)處理金流**。代幣扣款和注單結算是這個系統最容易出錯的地方,你會需要精準控制每一句 SQL、鎖的範圍和交易邊界。`sqlc` 讓你寫真的 SQL 但拿到型別安全的 Go code,是這類系統最好的折衷。
- **在 core 之外寫任何業務判斷**。一旦網頁「順手」算了一次賠率,規則就開始分裂。

## 5. PostgreSQL 設計要點

### 存取邊界

- **只有 core 有寫入權限**,而且只有 core 有連線憑證。
- 未來讀取變重 → 加 read replica,由 core 內部分流,呼叫端無感。
- 不要為了「方便」讓 Bot 直連資料庫。那一刻起這個架構就沒有意義了。

### 金額絕對規則

```sql
-- 代幣一律整數。永遠不要用 float / double / numeric with scale
balance BIGINT NOT NULL DEFAULT 0
```

**帳本是真實來源,餘額是快取:**

```sql
CREATE TABLE token_entries (          -- append-only,永不 UPDATE / DELETE
  id          BIGSERIAL PRIMARY KEY,
  user_id     BIGINT NOT NULL REFERENCES users(id),
  amount      BIGINT NOT NULL,        -- 正負皆可
  reason      TEXT   NOT NULL,        -- bet_stake / bet_payout / purchase / refund ...
  ref_type    TEXT,
  ref_id      BIGINT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`users.token_balance` 在同一個 transaction 內更新。另外排一個對帳 job,定期驗證 `SUM(token_entries.amount) = users.token_balance`,不符就告警。這個 job 很便宜,但會在你出事的第一時間告訴你。

### 併發控制

注單結算和扣款必須鎖:

```sql
SELECT token_balance FROM users WHERE id = $1 FOR UPDATE;
```

或對整場比賽用 advisory lock,避免同一場被重複結算:

```sql
SELECT pg_advisory_xact_lock(hashtext('match_settle'), $match_id);
```

### 冪等性(這個一定要有)

Discord 的互動會重送、使用者會連點、網路會重試。

```sql
CREATE TABLE idempotency_keys (
  key          TEXT PRIMARY KEY,
  request_hash TEXT NOT NULL,
  response     JSONB,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

所有會動到錢的 API 都要求帶 `Idempotency-Key`。相同 key 直接回傳上次的結果;key 相同但 request 內容不同 → 回 409。

### Outbox(整合的地基)

```sql
CREATE TABLE outbox_events (
  id           BIGSERIAL PRIMARY KEY,
  topic        TEXT NOT NULL,          -- match.started / bet.settled / tournament.finished
  payload      JSONB NOT NULL,
  status       TEXT NOT NULL DEFAULT 'pending',
  attempts     INT  NOT NULL DEFAULT 0,
  next_retry_at TIMESTAMPTZ,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON outbox_events (status, next_retry_at) WHERE status = 'pending';
```

領域變更和事件寫入在**同一個 transaction**:

```sql
BEGIN;
  UPDATE matches SET winner_id = $1, status = 'done' WHERE id = $2;
  INSERT INTO token_entries ...;
  INSERT INTO outbox_events (topic, payload) VALUES ('match.finished', $3);
COMMIT;
```

這樣就不會出現「比賽結算了但通知沒發」或「通知發了但結算 rollback」。多實例安全消費靠:

```sql
SELECT * FROM outbox_events
WHERE status = 'pending' AND next_retry_at <= now()
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 100;
```

`SKIP LOCKED` 是關鍵 —— 多個 dispatcher 同時跑也不會重複處理同一筆。

### 工具鏈

| 用途 | 選擇 | 理由 |
|---|---|---|
| Driver | `pgx/v5` + `pgxpool` | Postgres 原生協定,效能與功能都優於 `database/sql` |
| Query | `sqlc` | 寫真 SQL,生成型別安全 Go code,無 ORM 的黑魔法 |
| Migration | `goose` | 可 embed 進 binary,支援 Go migration |
| 測試 | `testcontainers-go` | 對真的 Postgres 跑測試,不用 mock |

### 資料成長

`token_entries` 和 `outbox_events` 是純增長的表。辦幾十場比賽還不用管,但預先想好:outbox 成功的紀錄保留 30 天後刪除,token_entries 按月分割表。

## 6. Redis 用途(以及不該用的地方)

| 用途 | 做法 | 備註 |
|---|---|---|
| 即時事件扇出 | Pub/Sub 或 Streams | 多實例的 SSE/WebSocket 廣播 |
| 賠率快取 | `HSET odds:{match_id}` | 投票變動時重算寫入,讀取全走快取 |
| 速率限制 | 令牌桶(Lua script 保證原子) | 註冊、下注、Bot 指令 |
| 任務佇列 | `asynq` | outbox 派送、排程、重試與退避 |
| 短期鎖 | `SET NX PX` | **只當最佳化**,一致性靠 Postgres |

**不要用 Redis 的地方:**

- **任何金額的真實來源。** 餘額快取可以放 Redis,但真值永遠在 Postgres。
- **需要送達保證的事件。** Redis Pub/Sub 是 fire-and-forget,訂閱者當下不在線就永久漏掉。要可靠請用 Redis Streams(有 consumer group 與 ACK)或直接用 Postgres outbox。這是很常見的踩雷點。
- **當成主資料庫。** 就算開了 AOF,它的持久性保證和 Postgres 不是同一個等級。

## 7. 整合層設計

所有外部服務都藏在同一個介面後面:

```go
type Notification struct {
    Channel  string          // email | sms | instagram | facebook | discord
    To       string
    Template string
    Data     map[string]any
}

type Sender interface {
    Send(ctx context.Context, n Notification) error
}
```

Dispatcher 讀 outbox → 依 topic 決定要發哪些通道 → 呼叫對應 Sender → 失敗則指數退避重試 → 超過上限進死信表並告警。

**加新平台的成本 = 實作一個 interface + 註冊路由規則。** 這就是這個設計的價值:LINE、Telegram、Threads 之後要加,不需要動任何領域程式碼。

| 通道 | 建議 provider | 難度 | 注意 |
|---|---|---|---|
| Email | Resend / SES | 低 | SPF、DKIM、DMARC 要設,否則進垃圾桶 |
| SMS(台灣) | 三竹簡訊 | 低 | 國際用 Twilio |
| Instagram | Meta Graph API | 中 | 只發自己帳號 → Standard Access,免審核 |
| Facebook 粉專 | Meta Graph API | 中 | 與 IG 共用同一套設定 |
| Discord | Webhook | 極低 | 最簡單,建議第一個做 |

## 8. Docker 配置

### 服務組成

```yaml
services:
  postgres:   # postgres:17-alpine,healthcheck: pg_isready
  redis:      # redis:7-alpine,appendonly yes
  migrate:    # 一次性 job,depends_on postgres service_healthy
  core:       # Go,depends_on postgres + redis healthy
  bot:        # Node 22-alpine,depends_on core healthy
  web:        # Next.js standalone,depends_on core healthy
  caddy:      # 自動 TLS,反向代理,注意 SSE 要關 buffering
```

### 建置策略與映像大小

| 服務 | 做法 | 預期大小 |
|---|---|---|
| core | 多階段 → `gcr.io/distroless/static` 或 `scratch`,`CGO_ENABLED=0` | 15–25 MB |
| bot | 多階段 → `node:22-alpine`,只複製 `dist` 與 production deps | ~120 MB |
| web | Next.js `output: 'standalone'` | ~180 MB |

### 要做對的細節

- **healthcheck + `depends_on: condition: service_healthy`**。沒有這個,core 會在 Postgres 還沒起來時就崩潰重啟,log 一片混亂。
- **非 root 執行**,能唯讀的檔案系統就設 `read_only: true`。
- **secrets 走 `env_file`**,絕不進映像、絕不進 git。
- **`restart: unless-stopped`** 搭配資源限制。
- **volume 只給 postgres 和 redis**,其他服務應該是完全無狀態的 —— 如果某個服務需要 volume 才能運作,那是設計有問題的信號。
- **開發用 `compose.dev.yaml` override**:core 用 `air` 熱重載、bot 用 `tsx watch`、web 用 `next dev`,原始碼掛載進去。

### 規模判斷

**單機 compose 撐得住幾百人同時在線。** 你的規模不需要 Kubernetes。等到需要多節點、需要滾動更新零停機、需要自動擴縮的時候再說 —— 而那一天可能不會來。過早上 k8s 是這類專案最常見的時間黑洞。

備份就是 `pg_dump` 排程 + 異地存放,並且**定期實際演練還原**。沒還原過的備份不算備份。

## 9. 風險清單

| 風險 | 影響 | 對策 |
|---|---|---|
| core 變成 CRUD 代理 | 整個架構失去意義 | Code review 守住:API 命名必須是業務動作 |
| 代幣算錯或重複扣款 | 玩家信任崩潰 | 帳本 + 冪等鍵 + 對帳 job + 對真 DB 的整合測試 |
| Redis Pub/Sub 漏事件 | 通知漏發,難以察覺 | 可靠路徑一律走 Postgres outbox |
| 契約漂移 | 三個服務對不上,難除錯 | proto 自動生成,禁止手寫共用型別 |
| 低估工時做到失去動力 | 專案停擺 | 照 M0→M5 分階段,每階段都能實際辦比賽 |
| Meta 設定卡關 | 社群整合延宕 | 排在最後;先用 Discord Webhook 驗證整個 outbox 流程 |
| 註冊被灌爆 | 假帳號、投票失真 | 速率限制 + 邀請碼或 Discord 綁定才給投票權 |

## 10. 建議的第一步

不要從 core 的框架開始。從**寫下領域規則**開始:

1. 把賽事狀態機的每一個轉換、每一個守衛條件寫成文件(哪個階段能做什麼、不能做什麼)。
2. 把代幣的每一種進出列成表(來源、金額、觸發條件、可否退回)。
3. 把注單結算的每一種結果窮舉(全中、任一落空、比賽作廢、比賽重賽)。

這三份文件寫完,core 的 `internal/domain/` 幾乎是照著翻譯。跳過這步直接寫程式,你會在第三個月發現「比賽重賽時已結算的注單怎麼辦」這種問題,而那時候改動成本已經很高了。

## 11. 先搞懂 Skill 怎麼省 token

這個觀念不先講清楚,後面的取捨都會做錯。

### 載入機制:漸進式揭露

Claude 不會把所有 skill 內容都塞進 context。它只常駐每個 skill 的 **name + description**(約 30–100 tokens),判斷相關時才載入完整的 `SKILL.md`,附帶的參考檔案與 script 則是需要時才讀。

**推論**:裝很多 skill 本身不貴,貴的是**單一 skill 寫太長**。因為 skill 一旦觸發就是整份載入,行數直接等於每次呼叫的成本。

實務準則:
- `SKILL.md` 本體控制在 **500 tokens 以內**
- 長內容拆成參考檔案,讓 Claude 需要時自己去讀
- description 寫精準 —— 這是唯一常駐的部分,寫太模糊會誤觸發,寫太窄會該用時不用

參考數據:`obra/superpowers` 在 2026 年 3 月做過一次 token 優化,14 個 skill 從 3,150 行壓到 977 行(減少 69%),而行為沒有退化。可見多數 skill 初版都寫得太長。

### 兩種省 token 的路線,價值差很多

| 類型 | 代表 | 機制 | 省的量 |
|---|---|---|---|
| **輸出壓縮型** | `i-have-adhd`、`caveman` | 直接讓每次回應更短 | 立即可見,但有上限 |
| **正確性型** | `grill-me`、`superpowers`、code review | 減少「做錯再重做」的來回次數 | 上限高很多 |

**第二類才是大頭。** 每一次「你剛剛改壞了,修一下」都是一整輪完整的來回成本 —— 讀檔、思考、輸出、你再驗證。superpowers 的 benchmark 顯示約 14% 的 token 減少,而那不是靠壓縮輸出,是靠一次做對。

對你這種**規則密集**的專案(代幣帳本、注單結算、階段守衛),正確性型的價值又更高,因為做錯的代價不只是重寫,是資料已經寫進資料庫了。

## 12. 視覺與畫面設計 Skills

依實際使用度排序,並標註對這個專案的適用性。

### 第一順位:Anthropic `frontend-design`(官方)

生態系中安裝數最高的設計 skill(2026 年初約 277,000+ 次安裝)。做的事是在寫任何 code 之前,**強迫先選定一個明確的美學方向**(brutalist、editorial、retro-futuristic、maximalist……),再照著執行。

它明確禁掉一批東西:
- 字體:Inter、Roboto、Arial、Space Grotesk

```bash
claude plugin add anthropic/frontend-design
```

**建議**:官方、免費、風險最低,先裝這個就好。

**對這個專案**:賽事網頁最容易掉進「又一個紫色漸層 SaaS 儀表板」的陷阱。這個 skill 主要幫你在配色、字體、整體視覺方向上做出有意圖的選擇。晉級樹的座標數學它幫不上忙 —— 那部分是幾何,不是品味。

### 第二順位(擇一補強)

| Skill | 定位 | 什麼時候需要 |
|---|---|---|
| `ui-ux-pro-max`(nextlevelbuilder) | 社群最多安裝的設計 skill。50+ UI 風格、161 組配色、57 組字體搭配,會依專案生成完整設計系統 | 你需要一次產出整套設計 token,而不只是方向指引 |
| Vercel Web Design Guidelines | **品質閘門**,不是創意方向。稽核 accessibility、UX、100+ 條規則 | 上線前的檢查關卡 |
| Vercel React Best Practices | 效能與 React 慣例 | Next.js 前端寫到中後期 |
| shadcn/ui skill(官方) | 元件庫專用 | 你決定用 shadcn/ui |
| 動畫效能稽核類 | layout thrashing、compositor 屬性、scroll-linked motion | 晉級樹加了動畫之後卡頓時 |

## 13. 正確性與 Token 效率 Skills

### `grill-me` — 這個專案最該裝的一個

Matt Pocock 的規劃 skill,是目前安裝數最高的規劃類 skill 之一(某目錄站統計 2026 年 8 月約 82 萬次安裝)。內容極短,只有幾行,但效果很大。

**行為**:
- 逐一提問(一次一題),把設計決策樹的每個分支走完
- **每個問題都附上它建議的答案** —— 你可以直接說「就這樣」,不必每題都解釋
- 能從 codebase 查到的事實,它自己去查,不浪費你的回合
- 在你確認雙方理解一致之前,不開始任何實作

**觸發方式**:只能手動 `/grill-me`(設了 `disable-model-invocation: true`),Agent 不會自己叫。

**什麼時候用 —— 這點很多人搞錯**:
在你**有想法但還沒寫出規格**的時候用,而不是在已經有完整計畫之後。模糊不是延後的理由,模糊正是它要吃掉的東西。如果你已經能精準描述要做什麼,你就不需要它了。

**對這個專案**:第 10 節說的「先窮舉領域規則再寫程式」,正是 `grill-me` 的標準用例。拿「比賽重賽時已結算的注單怎麼辦」這類問題來說 —— 這種洞你自己想很難想到,但被逼問時會浮出來。

**姊妹 skill**:
- `grill-with-docs` —— 同樣的訪談,但會讀你的 codebase,並把結論寫進 `CONTEXT.md` 和 ADR。**專案進到 M1 之後改用這個**,決策會自動留下紀錄。
- `wayfinder` —— 題目大到一個 session 裝不下時,先畫成地圖再逐區塊 grill。

**已知限制**:範圍太大時它會問出兩百個問題。解法是先把工作切小再逐塊 grill。另外 session 太長、context 快滿時,問題品質會下降。

### `i-have-adhd` — 輸出風格

ayghri 的 skill,本質是一份**只有 10 條規則的 markdown**:答案先講、步驟編號、不要開場白、不要收尾語、清單最多 5 項、錯誤就事論事。

```
❌「好問題!你遇到的問題很可能是因為……」
✅「auth middleware 有 bug。token 過期判斷用了 < 而不是 <=。修法:」
```

**用法建議**:與其當 skill 裝,不如直接寫進全域 `CLAUDE.md`:

```markdown
## Output style
Always follow the rules in the `i-have-adhd` skill:
action-first, numbered steps, no preamble, no closers, state restated each turn.
```

這樣所有專案都生效,也省掉一次 skill 載入。

### `superpowers` — 開發方法論(需要評估)

obra(Jesse Vincent)的 14-skill 方法論包,官方 marketplace 上約 476,000+ 次安裝。強制走五階段:clarify → design → plan → code → verify,包含 TDD 強制(先寫失敗測試)、subagent 執行、code review 關卡。

**優點**:對這個專案的核心痛點(金流正確性)非常對症。TDD 強制搭配 `testcontainers-go` 對真的 Postgres 跑測試,是我在第 5 節說的做法。

**要知道的三件事**:
1. **計畫模糊時會 thrashing。** 它會很有紀律地執行一個模糊的計畫。所以順序是 `grill-me` 先,`superpowers` 後。
2. **License 在 2026 年初從 MIT 換成 Elastic License 2.0。** 自己用完全沒問題,但不能包成託管服務轉賣。
3. **框架偏重。** 如果覺得太重,可以只抄它的幾個模式進自己的專案 skill,不必整包裝。

### `caveman` — 列出但不建議當主力

極端壓縮輸出風格,宣稱減少約 75% token。代價是可讀性大幅下降。

放進清單是因為它確實是目前少數**直接針對 per-session 成本**的方案。但對一個你要長期維護、還要回頭讀懂決策脈絡的專案,我不建議 —— 省下的 token 會在你三個月後看不懂當初為什麼那樣做的時候還回去。

## 15. 你應該自己寫的 Skill(最高價值)

這節是整個附篇最重要的部分。

通用 skill 的邊際價值有限 —— 它們解決的是「所有人都有的問題」。**真正省 token 的,是把你專案的規則寫成 skill**,這樣 Claude 每次都不用重問、你每次都不用重貼。

判斷標準很簡單:**如果你一週貼超過兩次同樣的說明,那就是一個該寫的 skill。**

針對這個專案,我建議寫這四個:

### `tournament-domain`
賽事狀態機的完整轉換表、每個階段的守衛條件、代幣進出的所有來源、注單結算的所有情境(全中、任一落空、比賽作廢、比賽重賽)。

這份就是第 10 節說的那三份文件。寫成 skill 之後,任何關於「這個階段能不能做 X」的問題都不用再解釋一次背景。

### `go-core-conventions`
pgx / sqlc / goose 的用法慣例、transaction 邊界規則、錯誤處理風格、命名規則,以及那條鐵律:**所有會動到錢的 API 必須有冪等鍵**。

### `contract-first`
「改 API 一律先改 `.proto` 再生成,禁止手寫共用型別。」

這條規則短到不像需要一個 skill,但它正是最容易在趕時間時被違反的規則 —— 而違反的代價(三個服務型別對不上)要幾週後才會顯現。

### `bracket-svg`
晉級樹的座標公式、佈局常數,以及不變式:**父節點必須精準置中於兩個子節點之間**。附上驗證這個不變式的測試。

這種幾何邏輯每次重新推導都會出錯,寫下來一次省很多。

### 撰寫規範

```
.claude/skills/tournament-domain/
├── SKILL.md              ← 500 tokens 以內
├── state-machine.md      ← 完整狀態表,需要時才讀
├── token-flows.md
└── settlement-cases.md
```

`SKILL.md` 只放:這是什麼、什麼時候用、最關鍵的三五條規則、以及「詳細內容看 X 檔案」。

## 16. 安全提醒

**`SKILL.md` 可以夾帶 prompt injection,附帶的 script 會用你 agent 的權限執行。** 這不是理論風險。

準則:
1. 裝第三方 skill 前,**實際打開 `SKILL.md` 讀一遍**。它是純文字,幾分鐘的事。
2. 優先選官方(Anthropic、Vercel)或知名作者的 skill。
3. 特別警惕會起背景服務或開 port 的 skill。**具體案例**:`claude-mem` 在 2026 年 2 月被社群安全稽核評為 HIGH risk,因為它的本地 worker 在 37777 port 跑一個**沒有認證**的 HTTP API —— 機器網路設定不當時,那個 API 是對外暴露的。
4. 這個專案會碰到資料庫憑證、Meta App secret、簡訊 API key。給 agent 的權限範圍要有意識,不要讓它能讀到 `.env`。

# 附篇二:Landing Page 與 2D/3D 混合

## 18. 先定義這個頁面的工作

在談任何視覺之前,先把這件事釘死:**首頁只有一個工作,讓人在報名截止前註冊。**

不是「介紹我們的賽事」,不是「展示伺服器有多酷」。任何不服務於那個按鈕的元素都是成本。

這個定義會直接推翻一種很常見的做法 —— 做一個炫技的 3D 開場,然後在下面放一個「了解更多」。那個頁面很漂亮,但它把使用者最想做的事推到了第二屏。

### Signature:狀態驅動的首屏

這是我建議的核心設計,而且它比任何 3D 特效都有說服力,因為它是**真的**。

同一個頁面在不同階段,讀起來應該是完全不同的頁面:

```
報名期      巨大的倒數計時 + 「已報名 14 人」+ 一個按鈕。其他全部讓路。
報名截止    倒數換成「名單已封存」,焦點轉向即將到來的抽籤時間。
抽籤中      即時:正在抽的籤位在畫面上亮起,名字一個一個落位。
準備期      對戰組合表 + 每組的即時賠率。開始賣「你覺得誰會贏」。
比賽開始    整個首屏變成即時賽況板。進行中的比賽有脈動的紅點。
賽事結束    冠軍 + 本屆最爆的一張串關注單 + 下屆預告。
```

資料你本來就有(`GET /api/state` 已經回傳這些),成本幾乎是零,但效果是「這個站是活的」。

一個具體的細節:**把最誇張的那張中獎注單放到首頁**。「觀眾甲 用 50 代幣串了 3 關,拿回 1,240」—— 這比任何文案都更能讓人想參與。

### 3D 該扮演什麼角色

最大的陷阱,講白一點:**粒子場 + 漂浮幾何體 + 漸層光暈**。加了 600KB、拖慢 LCP、跟你的產品零關係。這種 3D 現在多到成為一種視覺噪音。

好的 3D 是**內容本身**,不是背景。針對這個專案,最有力的選擇是:

**把晉級樹擠出成 3D。**

- 每一輪是一個深度層(z 軸),鏡頭略微斜視,你會看到整個賽事的縱深
- 冠軍路徑點亮成一條貫穿整個結構的光線
- 賽事推進時,鏡頭緩慢往決賽的方向推
- 尚未確定的節點是半透明的線框,確定後才實體化

它是資料視覺化,不是裝飾。而且 —— **你 2D 的座標數學可以直接複用**:x 和 y 完全不變,`z = (round - 1) × 深度間距`。第 8 節驗證過的「父節點必須置中於兩子節點之間」這條不變式,在 3D 裡照樣成立。

**備案**(如果 3D 賽程樹做起來太重):一個抽象的競技場體積,鏡頭緩慢環繞。比較通用,但至少不假裝有意義。

### 視覺延續

沿用原型已經建立的調性,別讓首頁和內頁像兩個網站:

| 角色 | 色值 | 用途 |
|---|---|---|
| 底 | `#17101F` 深茄紫 | 場景背景、fog 顏色 |
| 面 | `#241A30` | 卡片、節點 |
| 金 | `#FFC145` | 代幣、賠率、**冠軍路徑的光** |
| 薄荷 | `#3DE0A8` | 勝利、正向 |
| 玫瑰 | `#FF4D6D` | 進行中、脈動點 |

**3D 場景的光源要用同一組顏色。** 金色的主光 + 玫瑰色的邊緣光,場景才會和 UI 是同一個世界。這是最容易被忽略、也最容易讓整體崩掉的一點。

字體維持 Archivo(標題)/ Noto Sans TC(內文)/ IBM Plex Mono(數字)。倒數計時和賠率一律用 mono 的 tabular figures,數字跳動時才不會左右晃。

## 19. 2D/3D 混合的技術做法

### 三種混合方式,選第一種

| 方式 | 做法 | 評價 |
|---|---|---|
| **1. Canvas 當底層,DOM/SVG 疊上去** | canvas 絕對定位在後,所有文字是真的 DOM | **預設選這個** |
| 2. `<Html>`(drei)把 DOM 投影到 3D 座標 | 標籤跟著 3D 物件跑 | 少量使用,例如節點上的選手名 |
| 3. 全部畫在 canvas 裡(文字用 troika SDF) | 連文字都是 3D | **landing page 千萬不要** |

理由很實際:方式 1 的文字能被搜尋引擎讀取、能選取複製、能被螢幕閱讀器念出、能用 CSS 響應式。方式 3 全部沒有,而且首屏文字變成 canvas 的一部分,LCP 直接毀掉。

### 選型:R3F

你的前端是 Next.js,所以是 **React Three Fiber**。它不是 three.js 的競爭者 —— 它就是 three.js,用 React 元件表達。搭 `drei` 拿現成的 loader、controls、helper。

**WebGPU 的現況值得說清楚。** three.js 在 2025 年 9 月的 r171 推出可用於生產的 WebGPU renderer,2026 年 2 月的 r160 把它和 WebGL 並列。但 R3F 對 WebGPU 的支援程度,各方報導不一致 —— 有的說 R3F v8.16 已透過新的 Canvas prop 完整支援,有的說 2026 年初仍不完整。

**建議:預設用 WebGL2,不要糾結。** WebGL2 覆蓋率 97% 以上,而你的場景是幾十個方塊和幾條線,根本用不到 compute shader。WebGPU 對你是「持續觀察」,不是決策因素。

**一個要留意的方向**:three.js 的 shader 撰寫層正在從 GLSL 轉向 **TSL**(Three Shading Language),它用 JavaScript 定義、自動編譯成 GLSL 和 WGSL 兩種。新的材質功能會是 TSL 優先。所以如果你之後要寫自訂 shader,**直接學 TSL,不要學 GLSL 再遷移**。

### Next.js 的三個坑

**1. SSR 會直接炸掉**(`window is not defined`)。Canvas 必須 client-only:

```tsx
const Scene = dynamic(() => import('./Scene'), {
  ssr: false,
  loading: () => <Poster />,   // 靜態海報圖佔位
})
```

**2. 不要 `import * as THREE`。** 那會把整包拉進 bundle。具名匯入,讓 tree-shaking 有機會工作。

**3. 首屏文字必須是 DOM 而且先渲染。** LCP 元素絕不能是 canvas。

### R3F 的三個必知(這幾條直接決定順不順)

**1. 動畫用 `useFrame`,不要 `useEffect` + `requestAnimationFrame`。** 後者在元件卸載時不會正確清理,會漏。

**2. 每幀變動的東西用 ref 直接改 three 物件,不要 `setState`。** 這是 React 開發者最常犯的錯 —— 一秒 60 次 setState,幾秒內就把 frame rate 打爛。

```tsx
// ❌ 幾秒內幀率歸零
const [rot, setRot] = useState(0)
useFrame(() => setRot(r => r + 0.01))

// ✅
const ref = useRef<THREE.Group>(null)
useFrame((_, dt) => { ref.current!.rotation.y += dt * 0.2 })
```

**3. 重的 geometry / material 用 `useMemo` 包起來。** 沒包的話,父層一 re-render 就整個重建,GC 會慢慢吃掉你的場景。

### 效能預算

| 項目 | 預算 | 備註 |
|---|---|---|
| three.js bundle | ~150KB gzip 起跳,加 drei 約 200KB | 這是入場費,先確認值得 |
| 3D 資產總量 | < 1.5MB | glTF + Draco 或 Meshopt |
| 貼圖 | < 4MB | KTX2 / Basis 壓縮 |
| **Draw calls** | **< 50** | 見下方 |
| DPR | `dpr={[1, 2]}` | 3x 手機用 3x 渲染是 9 倍像素,肉眼看不出差 |
| 靜態場景 | `frameloop="demand"` | 沒在動就不要跑 60fps |

**Draw call 比三角形數重要 —— 這條最反直覺。** 場景在手機上卡,通常不是模型太細,是 draw call 太多。16 人賽制的晉級樹有 15 個節點,要用 `InstancedMesh` 一次畫完,不要開 15 個 mesh。

**GPU 資源一定要 dispose。** React 卸載元件**不會**釋放 GPU 記憶體。使用者在頁面間切幾次,記憶體就爬上去了。這是 3D 網頁最常見的生產環境 bug。

**後製特效是手機掉幀第一名。** Bloom、DOF、SSAO 全部很貴。想要發光效果,先試 emissive material 配一層 CSS blur —— 便宜十倍,遠看差不多。

### 降級策略(不是可選項)

| 情況 | 做法 |
|---|---|
| 不支援 WebGL | 靜態海報圖 |
| `prefers-reduced-motion` | 場景凍結在一個好看的角度,不轉 |
| 低階裝置 / 省電模式 | 降低實例數、關掉後製 |
| 分頁不可見 | 停掉 render loop |
| 捲出視窗外 | 停掉 render loop |

`prefers-reduced-motion` 特別要做。對前庭功能敏感的人,一個緩慢旋轉的 3D 場景會造成實際的生理不適 —— 這不是偏好問題。

### 載入順序

```
0ms      HTML + critical CSS → 首屏文字可讀(LCP 在這裡發生)
         同時顯示靜態海報圖當 canvas 佔位
~200ms   hydration
idle     掛載 canvas(requestIdleCallback 或 IntersectionObserver)
         海報圖 cross-fade 成即時場景
```

**鐵律:3D 永遠不能擋住 LCP。** 使用者在 3D 還沒載入完的時候,就該能讀到「報名還剩 3 天」並且按下按鈕。

### 骨架

```tsx
// Scene.tsx — 只在 client 載入
export default function Scene({ matches, phase }: Props) {
  const reduced = useReducedMotion()

  return (
    <Canvas
      dpr={[1, 2]}
      frameloop={reduced ? 'never' : 'always'}
      gl={{ antialias: false, powerPreference: 'high-performance' }}
      camera={{ position: [6, 3, 12], fov: 42 }}
      onCreated={({ scene }) => {
        scene.fog = new THREE.Fog('#17101F', 14, 34)
      }}
    >
      <color attach="background" args={['#17101F']} />
      <ambientLight intensity={0.35} />
      <directionalLight position={[4, 8, 6]} intensity={1.1} color="#FFC145" />
      <directionalLight position={[-6, 2, -4]} intensity={0.5} color="#FF4D6D" />

      <Suspense fallback={null}>
        <BracketMesh matches={matches} />   {/* InstancedMesh,一次畫完 */}
        <ChampionTrace matches={matches} /> {/* 冠軍路徑的金色光線 */}
      </Suspense>
    </Canvas>
  )
}
```

3D 座標直接沿用 2D 的公式:

```ts
const DEPTH = 4
const pos = (round: number, slot: number) => [
  nodeX(round),        // 與 2D 完全相同
  -centerY(round, slot) * 0.05,
  -(round - 1) * DEPTH,
]
```

| 項目 | 難度 | 人週 |

| | | **+5.5 人週** |

原本的 25 人週變成約 **30.5 人週**。

**強烈建議:先做純 2D 版本上線,3D 排成 M6。**

狀態驅動的首屏(那 1.5 人週)本身就已經很有力 —— 一個會倒數、會顯示報名人數、會秀出最爆注單的頁面,轉換率不會輸給 3D。3D 是錦上添花。

**判斷點**:等你真的辦過兩三場比賽、知道玩家實際在意什麼之後,再決定 3D 要做成什麼樣。那時候你對「什麼值得放在首屏」的判斷,會比現在準得多。

# 附篇三:避免通用化視覺(AI 感)

## 21. 為什麼會有 AI 感

模型在沒有其他訊號時,輸出的是**設計決策的統計中位數**。它不是做了壞選擇,它是沒有做選擇 —— 落在眾數上。

這推出一條很實用的準則:

> 對模型說「不要做 AI slop」沒有用。
> 說「**這個具體的 pattern 是 AI slop,不要產出**」才有用。

籠統的品味指令會被中位數吞掉。具體的反例清單不會。這也是為什麼下面第 23 節是一份很長很具體的清單,而不是幾句原則。

### 最重要的一點:反 AI 感的建議本身變成了新的 AI 感

這點我上一節沒講,但它會直接修正我先前的建議。

- **2024 年的 tell**:紫色漸層 + 深色 hero + Inter
- **2026 年上升最快的 tell**:暖奶油背景 + 襯線標題(Instrument Serif / Fraunces / Playfair)+ 鼠尾草綠或陶土色

第二個之所以出現,是因為**前一波反 slop 建議全部收斂到那裡** —— 包含 Anthropic 自己的 `frontend-design` skill。現在社群一眼就認得出來,把它叫做「AI 試圖表現得有品味」的樣子。

所以真正的判準不是黑名單:

> **tell 是「沒被指定的預設」,不是「被禁的顏色」。**
> 你真的選過的紫色,通過。

這句話把整件事從「背一份禁用清單」變成「每個決定都要能回答:為什麼是這個,而不是預設的那個?」

### 你的專案已經有一半免疫

原型建立的那套 —— 深茄紫底、琥珀金、薄荷綠、玫瑰紅,搭 Archivo / Noto Sans TC / IBM Plex Mono —— 不在任何預設清單上,而且是為了「深夜賽事轉播台」這個主題選的。

這不是運氣,是**它有被選過**。

現在要做的不是重新設計,是**把它鎖起來**,讓後續開發沒有重新決策的空間。決策空間就是模型往中位數漂移的空間。

## 22. Skill 選型(修正第 12 節)

社群把反 slop 的工具分成三層。**不要全裝** —— 它們爭奪同一個決策位置,疊三四個以上會互相打架,結果是各出一半。

### 第一層:base taste layer(擇一)

| Skill | 特點 | 顧慮 |
|---|---|---|
| `frontend-design`(Anthropic 官方) | 免費、風險最低,強制先承諾一個美學方向、禁用預設字體。被稱為「大家都同意的地板」 | 存在明確批評:它自己收斂到 cream + serif 那一套,有人認為它現在正在生產它本來要防止的東西 |
| `design-taste-frontend`(Leonxlnx `taste-skill`) | 目前最多星的第三方設計 skill(約 75,800 stars,13 個 skill 合計約 300 萬次安裝,這一個約 35 萬次)。v2 是 2026 重寫版,規則更嚴 | v2 標示為 experimental,規則措辭仍在變動 |
| `impeccable` | 用 **anti-pattern** 教學 —— 明確列出玻璃擬態、側邊 tab 邊框、spark line 這些具體 pattern。另有 Chrome extension 可在真網站上標出 slop | 第三方,裝之前讀過 SKILL.md |
| `unslop-ui` | **最特別:它拒絕規定一種樣子。** 只標示「未經指定的預設」,同時點名 2024 的紫漸層和 2026 的 cream+serif 兩種預設 | 需要你自己提供方向或參考 |

**給你的建議**:因為你已經有鎖定的 design token,base layer 的邊際價值下降很多。選一個當保險就好 —— 我會選 `unslop-ui` 或 `impeccable`,因為它們是「審查」導向,不會跟你既有的方向打架;`frontend-design` 和 `taste-skill` 是「指導方向」導向,你已經有方向了。

### 第二層:token 系統 ← 對你最重要

你自己的。見下節,我已經寫好了。

### 第三層:回饋迴路

讓模型產出後自己對照清單打分。這是 `slop-review.md` 在做的事。

**社群的共識值得引用一句**:skill 設定的是**美學地板**,能把輸出拉到「看起來像資深的人做的」。但品味來自理解限制條件,不是來自一份禁用字體清單。**要往哪個方向走,判斷還是你的。**

## 23. 已產出的專案 Skill

我把上面的東西寫成了可以直接放進 `.claude/skills/` 的檔案:

```
.claude/skills/tournament-design-system/
├── SKILL.md          # 入口,三條硬規則,控制在 500 tokens 內
├── tokens.md         # 鎖定的配色、字體、間距、動態、簽名元素
├── vernacular.md     # 主題語彙:賠率單、記分板、票根、籤位
└── slop-review.md    # 具體的 tell 清單,PR 前跑一遍
```

設計上刻意遵守第 15 節自己訂的規範:`SKILL.md` 很短,三份長內容當參考檔案,需要時才讀。

### `SKILL.md` 的三條硬規則

1. **只用 token 定義的 CSS 變數,禁止任何一次性 hex 值。** 需要新顏色先問人。
2. **字體只有三個角色,不新增。** 數字一律 mono + `tabular-nums`。
3. **產出畫面前先讀 `slop-review.md` 自我檢查。**

第 1 條是整套裡最有效的一條。一次性 hex 值就是模型在做未經指定的決策,那正是 tell 的定義。

### `vernacular.md` 的核心

不要從「什麼風格」開始,從**主題自己的世界**開始:

| 來源 | 借什麼 |
|---|---|
| 運彩投注站的紙本賠率單 | 密集等寬數字、嚴格行列對齊、直角欄位 |

**借的是結構與質感,不是主題樂園式的直譯。** 賠率欄位用等寬數字右對齊,是借了賠率單的資訊密度;把整頁做成泛黃紙張加咖啡漬,是 cosplay。

### `slop-review.md` 涵蓋的 tell

配色(AI 紫、cream+serif+sage、漸層文字、深色+霓虹)、
字體(11 個具名禁用字體)、
版面(hero+三卡+CTA 骨架、卡中卡、什麼都圓角、未改過的 shadcn 預設樣貌)、
裝飾(玻璃擬態、側邊 tab 邊框、spark line、emoji 當 icon)、
動態(全部 fade-up + stagger)、
文案(開場清嗓、二元對比句型、戲劇性斷句、**句長節奏一致**)。

最後那條值得特別說:**句長節奏一致是 2026 存活最久的文案 tell**,也最難自己看出來。朗讀一遍最快抓到 —— 如果每句都差不多長、每句都在同一個節拍上落地,就是它。

# 附篇四:模組化與響應式

## 25. 一個必須現在決定的事:主題要能不重新部署就換掉

你說「先模組化,後續各活動客製視覺」。這個順序是對的,但它藏了一個決定,而且**現在不決定,之後要付三倍代價**:

> 主題是**資料**,還是**程式碼**?

如果是程式碼,每辦一個新活動就要改 CSS、跑 CI、重新部署。如果是資料,主題存在資料庫裡,換活動就是換一筆 JSON。

**選資料。** 而這個選擇會反過來規定 token 要怎麼寫。

### 三層 Token

```
第 1 層  原始值        --plum-900: #17101F
                       ↑ 主題只切換這一層
第 2 層  語意 slot     --surface-base: var(--plum-900)
                       ↑ 元件只能碰這一層
第 3 層  元件變數      --bracket-node-bg: var(--surface-raised)
                       (只在某個元件真的需要偏離時才建)
```

**鐵律:元件禁止引用第 1 層,禁止寫死 hex 值。**

這條不是潔癖。它是「換主題」這件事能不能成立的唯一前提 —— 只要有一個元件寫死了 `#241A30`,那個元件在新主題下就會變成一塊突兀的深紫色補丁。

### 流程

```
tournaments.theme (JSONB)
      ↓  core 隨 /api/state 回傳
      ↓  web 注入一段 <style>,覆寫第 1 層
      ↓  語意 slot 自動跟著變
      ↓  所有元件外觀改變,程式碼零改動
```

注入點只有一個地方:

```tsx
<style>{`[data-theme="${t.id}"]{${toCssVars(t.theme)}}`}</style>
```

### 主題契約:不是什麼都能改

開放太多,每個活動的版面都會壞掉。

| 可自訂 | 不可自訂 |
|---|---|
| 第 1 層色值(6 中性階 + 3 語意色) | 間距與字級尺度 |
| 顯示字體 | 內文字體、`--font-mono` |
| 圓角尺度(`0` = 全直角) | **語意色的職責** |
| 背景紋理 | 元件結構與互動模式 |
| 首頁 3D 場景變體 | |

**最後那條最重要:可以改「金色是哪個金」,不能讓金色代表勝利。**

`--font-mono` 不開放,因為賠率欄位對齊是功能不是風格。間距不開放,因為一旦可調,版面必壞。

**跨活動的一致性本身就是價值** —— 玩家換一個活動,不該要重新學怎麼下注。客製的是外觀,不是產品。

## 26. 手機版:不是把桌機縮小

### 賽程樹(最難的一個)

16 人賽程樹大約 1000 × 700px。塞進 375px 螢幕只有三種下場:看不清、要一直捏放大、或縮到字看不見。

**手機要的是不同的資訊佈局,不是同一張圖的縮小版。**

| 尺寸 | 做法 |
|---|---|
| ≥ 1024px | 完整樹狀圖,一眼看到全貌 |
| 768–1023px | 完整樹 + 橫向捲動,黏住輪次標題 |
| < 768px | **分輪檢視** —— 一次一輪,頂部有輪次切換 chip |

分輪檢視的關鍵細節:
- 預設落在**有事情正在發生的那一輪**,不是第 1 輪
- 每場是一張全寬卡片,兩位選手上下排列,右側賠率
- 提供「我的賽程」篩選,只看自己那條路徑

用捏放大的完整樹是把設計問題丟給使用者。

### 投注單

桌機是右側 dock;手機是**底部 sheet**,收合時是一條 bar:`3 關 · 4.82× · 可拿 482`。

理由很實際:拇指在螢幕下方。所有博弈類 app 都這樣做,不是因為好看。

必做,否則 iPhone 的 home indicator 會蓋住送出按鈕:

```css
padding-bottom: calc(var(--space-4) + env(safe-area-inset-bottom));
```

### 管理介面有個容易被忽略的現實

看起來管理頁是桌機優先。但**辦活動的人是站在現場拿著手機的。**

所以「開始 / 重開 / 判定勝者」這三個操作必須在手機上好按:全寬、分行、間距夠大。判定勝者要二次確認 —— 誤按會直接結算所有注單,那是無法優雅回復的。

階段切換、建立賽程這類「坐著做」的操作,可以桌機優先。

### 斷點:版面用 media query,元件用 container query

```css
.match-card { container-type: inline-size; }
@container (min-width: 380px) { .match-card__odds { display: block; } }
```

同一張比賽卡會出現在右側 dock(340px)、手機全寬(375px)、桌機主區(600px)。
它該看**自己的容器**有多寬,不是看螢幕。用視窗斷點會在 dock 裡出現「螢幕是桌機但卡片其實很窄」的錯誤佈局 —— 這是響應式最常見的隱形 bug。

## 27. 元件庫怎麼切

```
packages/ui/                 純展示,可跨活動重用
├── primitives/              Button, Input, Chip, Sheet, Dialog
└── patterns/                OddsRow, MatchCard, BracketTree, BetSlip, PhaseRail

services/web/features/       有業務邏輯,組合 ui/
├── bracket/
├── betting/
└── admin/
```

**分界線只有一條,但必須守住:**

> `packages/ui` 不 import 任何 API 型別、不呼叫 fetch、不知道賽事規則。它只收 props。

一旦 `MatchCard` 裡面出現 `if (phase === 'IN_PROGRESS')`,它就綁死在這個產品的當前規則上,之後任何客製都要動它。

### 元件檢視:用一個路由,不要用 Storybook

「各活動客製視覺」需要一個地方能一次看到所有元件在所有主題下的樣子。

Storybook 能做,但對單人專案是持續的維護成本(設定、相依、每個元件要寫 story、還要跟主 app 保持同步)。

**更划算的做法:一個 `/kitchen-sink` 路由**,渲染每個元件的每種狀態,頂部放主題切換器和尺寸切換器。

- 成本約 2 天,Storybook 約 1 週加上長期維護
- 它跑在真的 app 裡,用真的 token,不會有「Storybook 裡好好的、app 裡壞掉」的問題
- 新增主題時,套上去捲一遍就知道有沒有東西破版

### 一條 CI 規則(擋住主題功能被慢慢弄壞)

```bash
# 元件層禁止一次性 hex 與原始色階
grep -rEn '#[0-9a-fA-F]{6}|var\(--(plum|amber|mint|rose)-' packages/ui/src \
  && { echo "元件只能用語意 slot"; exit 1; }
```

粗暴但有效。這種紀律靠自律撐不過三個月,靠 CI 可以。

| | | **+5.0 人週** |

總計約 **35.5 人週**。

### 但這筆帳要這樣看

**這 5 人週裡,大部分不是「額外的工作」,是「換一種方式做同一件工作」** —— 前提是從一開始就這樣做。

從第一行 CSS 就用語意 slot,和先寫死顏色再回頭抽出來,前者幾乎不多花時間,後者要 2–3 倍,而且回頭抽的時候一定會漏掉幾個,那幾個就變成之後每次換主題都要重修的地方。

所以這是典型的「現在做,或之後付三倍」類別。你說要先模組化,判斷是對的。

**唯一該延後的是主題管理介面**(那 1 人週)。第一個活動直接寫 JSON 進資料庫就行,等真的辦到第三場、確定哪些東西真的需要換,再做 UI。

### M1 · 辦成第一場比賽 — 9.5 人週

### M8 · 3D(選配) — 4 人週

---

### 拆出 core 服務 — 條件觸發,約 4 人週

**這件事沒有固定時程,而且可能永遠不需要。**

我在第 1 節提的三服務架構是**目標形狀**,不是起手式。只要 M1 的單體有把領域層和 HTTP 層分乾淨,Discord Bot 直接呼叫它的 API 就行了 —— 那已經是「core + 呈現層」的關係,只是還住在同一個行程裡。

1. 網頁和 Bot 需要不同的部署節奏(改 Bot 不想重啟賽事服務)
2. 單體的建置或測試慢到影響開發
3. 有第二個人加入,需要獨立的工作邊界

沒有這些訊號就拆,你付的是分散式系統的代價,換到的是零。

# 附篇六:修正版架構(取代第 0、1、2 節)

> 「Discord Bot 跨活動長壽、網頁隨活動替換」這個條件,翻轉了原本的假設。
> 原本假設賽事是核心、Bot 是薄轉接層;實際上 **Bot 是長壽的基礎設施,網頁是耗材**。
> 本篇取代第 0 節的判斷二、第 1 節的服務拆分、第 2 節的 repo 數量。

## 33. 真正的切線:平台層 vs 活動層

不是 Bot vs Core,是**長壽 vs 逐活動**。

| 平台層(跨活動) | 活動層(每次替換) |
|---|---|
| 身分、帳號、Discord 綁定 | 賽事規則、階段狀態機 |
| **代幣帳本** | 賽程樹、抽籤、晉級 |
| 通知管線(outbox、email/SMS/IG) | 賠率、投票、注單 |
| 獎勵兌換 | 配置、賽中商店 |
| Discord 互動閘道 | 網頁前後端 |

**代幣帳本必須在平台層。** 玩家在賽事賺的代幣,下個活動要能用 —— 不然每辦一次就歸零,累積代幣就沒有意義了。

## 34. Discord Bot 重新定位:通用互動閘道

要服務未來所有活動,它就**不能知道任何一個活動的規則**。只做三件事:

1. 收 Discord interaction,依指令命名空間路由到對應的活動服務
2. 把活動服務回傳的「要顯示什麼」渲染成 Discord 元件
3. 收 outbox 事件,發到頻道

活動服務回傳**描述**,不是 Discord 格式:

```json
{ "title": "阿凱 對 小美",
  "fields": [{"k":"賠率","v":"1.43 / 2.58"},{"k":"票數","v":"18"}],
  "actions": [{"id":"summer-cup:bet:5:1","label":"押 阿凱","style":"primary"}] }
```

`custom_id` 前綴就是路由鍵。加新活動 = 註冊一個前綴 + 實作這個回傳契約,**Bot 一行都不用改**。

### 語言:改回 TypeScript + discord.js(推翻第 0 節判斷二)

第 0 節選 Go 的兩個理由,在新定位下都不成立了:

| 原本的理由 | 為什麼失效 |
|---|---|
| Bot 很薄,語言不重要 | 它不薄了,它是長壽的渲染層 |
| 用 Go 能直接 import core 的 domain 型別 | 它不 import 任何 domain 型別,只認渲染契約 |

剩下的判斷變成:主要工作是 Discord 元件渲染,那正是 discord.js 領先最多的地方。而且長壽代表你會持續想要新的 Discord 功能,discordgo 的落差會累積。

## 35. Repo:4 個

| Repo | 語言 | 生命週期 | 職責 |
|---|---|---|---|
| `hestia` | Go | 長壽 | 身分、代幣帳本、通知管線、兌換、契約定義 |
| `stentor` | TypeScript | 長壽 | 互動閘道 |
| `themis` | Go | 逐活動 | 活動規則、狀態機、結算 |
| `theatron` | TypeScript | 逐活動 | 活動前端 + 共用元件庫 |

```
hestia/
└── contracts/                 # 平台 API + 渲染契約(唯一來源)

stentor/                   # 只認渲染契約

themis/
└── activities/
    ├── 2026-summer-cup/
    │   └── api/openapi.yaml   # 該活動的契約
    └── 2027-guild-war/

theatron/
├── packages/ui/               # 跨活動元件庫與 design token
└── activities/
    ├── 2026-summer-cup/
    └── 2027-guild-war/
```

`themis` 和 `theatron` 各自裝多個活動。**辦新活動是複製資料夾,不是 fork repo。**

### 命名一路帶到底

| | |
|---|---|
| Go module | `github.com/<you>/hestia` |
| 容器與映像 | `hestia`、`themis` |
| 環境變數前綴 | `PLATFORM_`、`ACTIVITY_` |
| 生成的 TS client | `@<org>/summer-cup-api` |

## 36. 切開之後的代價:契約會漂

Go 和 TS 分兩個 repo,代表**活動的 API 契約跨了兩個 repo**。改一個欄位要開兩個 PR,而且兩邊 CI 都綠也不代表接得起來。

必須用工具擋住:

```
themis/activities/2026-summer-cup/api/openapi.yaml   ← 唯一來源
  ├─ oapi-codegen   → Go server 骨架(同 repo)
  └─ CI 發佈 npm    → @<org>/summer-cup-api@x.y.z
                       theatron 用版本相依安裝
```

**規則:`theatron` 禁止手寫 API 型別,只能 import 生成的 client。**

這和「元件禁止寫死 hex」是同一類紀律 —— 變成 CI 檢查,不靠自律。

### 三份契約的歸屬

| 契約 | 住哪 | 誰依賴 |
|---|---|---|
| 平台 API(身分、帳本、通知) | `hestia` | 其餘三個 |
| **渲染契約**(Discord 顯示描述) | `hestia` | `stentor`、`themis` |
| 活動 API | `themis/activities/<活動>/api/` | `theatron` |

渲染契約放 `hestia` 是關鍵。放 `stentor` 的話,每個新活動都要去改 Bot 的 repo,分 repo 的目的就沒了。

## 37. 資料庫:不切

**Bot 碰不碰 DB**:絕對不碰,連線字串都不該有。Bot 暴露在外部平台,它被打下來時不該連著資料庫。

**平台與活動要不要拆成兩個 DB**:現在不要。理由是這個:

> **下注 = 扣代幣(平台)+ 建注單(活動)。這兩件事必須原子。**

同一個 DB → 一個 transaction 解決。
拆成兩個服務 → saga、補償交易、部分失敗,為了還沒發生的需求付很真實的代價。

做法是**推遲但不放棄**:同一個 Go 服務、同一個 DB、**兩個 schema**(`platform` / `activity`),模組邊界硬性隔開。帳本用 in-process interface:

```go
type Ledger interface {
    Debit(ctx context.Context, userID int64, amount int64, idem string) error
}
```

之後真要拆,實作換成 HTTP client,呼叫端一行不改。

**什麼時候真的該拆**:要**同時跑兩個活動**的時候。在那之前拆是純成本。

## 38. 演進路徑(修正第 29 節)

| 時機 | Repo 數 | 說明 |
|---|---:|---|
| M1 | **2** | `hestia`(平台 + 第一個活動同居)+ `stentor` |
| 第二個活動 | **4** | `internal/activity/` 抽成 `themis`,前端抽成 `theatron` |

M1 不要一開始就開四個。單體裡先用硬性模組邊界:

```
internal/platform/    ← 不能 import activity
internal/activity/    ← 只能透過 interface 用 platform
```

邊界守住,之後抽出來是搬資料夾,不是重寫。

**`stentor` 例外,從第一天就獨立。** 住在同一個 repo 裡,它一定會直接 import 賽事型別,那就再也拆不出來了。從 M3 開始就照「通用閘道」寫,不要出現任何 `if 賽事階段 == ...`。這是唯一現在就要付的額外成本,約 0.5 人週,但它決定 Bot 能不能真的複用。

## 39. 誠實的成本評估

四個 repo 對單人維護是四套 CI、四套 secrets、四套部署設定。約多 1 人週的建置,加上持續的切換負擔。

**值不值得,取決於 `themis` 和 `theatron` 的替換節奏是不是真的不同步。** 如果每次辦活動兩邊都一起改一起上,合成一個 monorepo 會輕鬆很多 —— Go 和 TS 同 repo 沒有技術問題,path filter 就能分開 CI。

如果之後發現 Bot 其實只服務這個平台、沒有做其他遊戲內容,那把它併回 `hestia` 也是合理的簡化。

**唯一不該妥協的是模組邊界。** repo 怎麼切可以之後再調,`platform` 不能 import `activity` 這條線一旦破了,就再也回不去了。

## 40. Repo 命名

取自古希臘的公開賽會 —— 這不是硬套的主題,古希臘賽會就是這套神話的原生場景。

| **stentor** | 《伊利亞特》的傳令官 | Discord 互動閘道 | 銅嗓,聲音抵得過五十人;英文 stentorian 即由此而來。他只負責喊,不參與決策 |

**Hestia 與 Themis 的對比是這套最好的地方**:灶火恆常,律法隨時代修改 —— 正是平台層與活動層的關係。

## 41. 這套命名付出的代價

**一、名字不再暗示職責。** `tallyroom` / `prizering` 聽了大概能猜,`themis` 完全猜不到。HashiCorp 那套好用,是因為 Vault 一聽就知道存密鑰;希臘神話拿氣氛換掉了這個。

對一個遊戲伺服器的專案,這個交換可能划算 —— 氣氛本來就是產品的一部分。但要知道付了什麼。

**二、希臘神話是軟體界撞名最兇的命名池。** Hermes、Atlas、Prometheus、Hydra、Chronos、Janus 全被大專案佔走。挑的這四個相對乾淨,但 `themis` 與 `hestia` 各有一些中小型專案在用。自己的 org 底下不衝突,只是搜尋時會有雜訊。

## 42. 代號的邊界

代號只活在**開發者之間**。跨過那條線就回到直白。

| 場合 | 用法 |
|---|---|
| README 第一行 | `# hestia`,**下一行必須是** `平台核心:身分、代幣帳本、通知管線`。代號好用的前提是對照表隨手可得 |
| 環境變數 | `PLATFORM_DATABASE_URL`,**不要** `HESTIA_DATABASE_URL`。凌晨三點看 log 的人不該還要查神話辭典 |
| 容器與映像 | `hestia`、`themis` —— 這是開發者看的,可以用代號 |
| 套件內部路徑 | 照舊 `internal/platform/`、`internal/activity/` |
| 錯誤訊息與使用者介面 | 一律白話,代號絕不外露 |
| 活動資料夾 | `2026-summer-cup`,**不跟著取代號** |

最後一條特別重要:活動本身已經有名字(夏季盃、公會戰),再疊一層代號,半年後你會查不到「phoenix 是哪一場」。

**代號給長壽的骨架,清楚的名字給會累積的內容。**

## 43. 命名原則(之後新增服務時照這個判斷)

從業界慣例歸納出的三條:

1. **選一個世界,全部待在裡面。** HashiCorp 是工匠與旅程(Terraform、Vault、Consul、Nomad);Netflix 是神話守門人加靈長類(Zuul、Eureka、Hystrix、Chaos Monkey)。單一名字好不好不是重點,**整組看起來像同一個人取的**才是。
2. **名字要斜著說出職責。** Vault 存密鑰、Envoy 是代理、Snowflake 產唯一 ID、Spanner 跨全球。共通點:別人講一次,你就永遠記得。
3. **不要用實作命名。** `redis-cache-service` 在你換掉 Redis 那天就變成謊言。綁職責,不綁技術。

加上兩條務實的:念得出來(每天要口頭講),以及動手前先查 GitHub、npm、Go module 的衝突。

新增服務時保持在賽會與神話這個世界裡,並讓字元數落在 5–9 之間。
